# Bullet revision ledger

The editable document is a `ResumeVariant`, where the current application stores
`bulletEdits`. In these APIs `resumeId` means that variant's MongoDB `_id`, not
its public `variantId`, the profile ID, or an upload session ID. Every operation
requires the existing Bearer authentication and checks document ownership.

- `GET /api/v2/resume/:resumeId/revisions` returns `{ success: true, data: {
  currentVersion, revisions } }`. Revisions are chronological and include actor
  `userId`, section, monotonically increasing version, timestamp, server ATS score,
  RFC 6902 `patch` and `inversePatch`. The oldest retained record also includes a
  `baseSnapshot` representing the state **before** its patch. Apply successive
  patches to reconstruct each retained version; inverse patches undo them.
- `PUT /api/v2/resume/:resumeId/sections/:sectionId/bullets` explicitly saves a
  section and automatically records its revision. Body: `{ expectedVersion: 0,
  bullets: [{ bulletIndex: 0, originalText: "Original", editedText: "Improved" }] }`.
  An empty array deletes that section. Sections are lowercase, up to 50 characters,
  starting with a letter and containing letters, digits, spaces, `_` or `-`.
  The complete document retains the existing 200-bullet limit. Scores and patch
  operations are generated by the server, never accepted from the client.
- `POST /api/v2/resume/:resumeId/revisions/:version/restore` accepts
  `{ expectedVersion }`. It reconstructs the selected version, restores that
  record's section while preserving later changes to other sections, recomputes
  the current ATS score, and creates a new revision with `restoredFrom`.

These endpoints also have v1 and deprecated unversioned aliases. Reads use the
existing resume read budget; writes use the resume processing budget. Responses
are private/no-store. Unknown documents, foreign documents and unavailable/pruned
versions return 404. Stale expected versions return 409. New and legacy variants
start at version 0. Identical explicit saves do not consume versions; restores
always create a record, including when the content already matches.

The existing flag-gated live-editor variant-generation save automatically records
its initial edits as a whole-document checkpoint (`sectionId: "*"`). Restoring
that checkpoint restores all its bullets. Legacy variants need no migration:
their first explicit section save captures the previous bullets as its baseline.
Version 0 can restore that entire baseline while revision 1 is still retained,
allowing the very first edit to be undone. Once pruned, version 0 returns 404.
The new revision API supports explicit saves; no browser autosave timer is added.

Resume updates, ledger insertion and pruning use one MongoDB transaction with a
version check. MongoDB must support transactions (replica set or sharded cluster);
there is no non-transactional fallback. Concurrent writers using the same expected
version cannot silently overwrite each other. The initial variant-generation
engine still creates a variant before its ledger transaction; if that transaction
fails, the request fails and an unedited generated variant can remain.

At most 50 revision records are retained **per variant**, across all sections.
Pruning advances the oldest baseline in the same transaction before deleting old
patches, so every retained version remains reconstructible. Version numbers are
stored on the variant and never reused after pruning. Historical scores remain
the score at save time; restores are rescored against current profile/keywords.

Validation from `backend/`: `npm run build` and
`npm test -- src/__tests__/modules/resume/bulletRevision.test.ts src/__tests__/modules/resume/variant-v2.test.ts`.

## Stateless score preview

`POST /api/v2/resume/diff-score` (also v1 and the deprecated `/api` alias) accepts:

```json
{
  "originalBullets": ["Built reliable APIs for customers across multiple regions"],
  "revisedBullets": ["Built reliable Node.js APIs for customers across multiple regions"],
  "targetKeywords": ["Node.js"]
}
```

The response is `{ success: true, data: { originalScore, revisedScore, delta,
keywordChanges: { added, removed }, brevityScore, originalBrevityScore } }`.
`delta` is a signed JSON integer; clients can add a `+` display prefix. Brevity
scores describe each list's bullet length and fluff phrases. All scores are
0–100; empty bullet lists score zero. The calculation comes directly from the
browser-compatible `@devtrack/ats-core` utility; its README documents the complete
heuristics, including keyword stuffing penalties. This preview does not save
edits or change the full-resume scoring used by the revision ledger.

Zod rejects unknown fields, missing arrays, non-string entries, more than 100
bullets per list, bullets over 1,000 characters, combined original/revised text
over 50,000 characters, more than 100 keywords, and empty or over-80-character
keywords. Keyword labels are trimmed. Responses are private/no-store.

The route verifies a Clerk Bearer **session** token without loading or syncing a
MongoDB user. Its handler and scoring utility perform zero MongoDB operations.
Only caller-supplied text is processed; there is no stored resume/ownership lookup.
The existing expensive-generation limiter is not consumed. The shared read limiter
uses its IP fallback (120/minute), and the router's existing read-ingress IP guard
applies (600/minute); other API routes retain their existing limits. Those guards
use Redis; the scoring calculation itself has no external dependencies.

For networkless authentication, set `CLERK_JWT_KEY` to your Clerk instance's PEM
public key. The origin in the token must match `CORS_ORIGIN` when configured.
Without `CLERK_JWT_KEY`, verification uses `CLERK_SECRET_KEY` and Clerk's JWKS
fetch/cache. That remote authentication latency is outside the pure scoring
budget. No private key is needed by the server.

Run `npm run test:score-differential` from `backend/` for database-free route tests
using real JWT verification with a locally generated RSA fixture key. Invalid
signatures, expired/future tokens, unauthorized origins, invalid input, version
aliases, rate-limit handling, and forbidden MongoDB access are covered.
`npm run test:unit` includes these tests through their dedicated configuration.
Run `npm run test -w @devtrack/ats-core` from the repository root for pure-engine,
legacy-score, and browser-bundle regression tests.

For an opt-in local benchmark, set `ATS_BENCHMARK=1` and run
`npm run test:score-differential`. It measures 1,000 calculations and 1,000 local
HTTP requests for both a typical input and a near-limit 50,000-character/100-keyword
input, after warmup, using Node's HTTP client with one keep-alive connection. It
requires pure p95 < 15ms and local HTTP p95 < 20ms. HTTP measurements include actual
RSA JWT verification and JSON parsing/serialization,
but stub Redis rate-limit calls and exclude internet/proxy/TLS overhead. Production
latency, live Clerk enrollment, and browser editor integration require separate
verification. The endpoint does not add an editor debounce or UI.
Tests use owned temporary MongoDB replica sets and stub authentication/rate-limit
boundaries; no live Clerk or AI credentials are required.

## ACR bullet suggestions

`POST /api/v2/resume/bullets/suggest` accepts an authenticated Clerk session mapped
to a local user. Existing v1 and unversioned aliases also work. The global API
limiter and `rateLimiters.expensiveAction` apply, including to cache hits.
The latter uses the existing shared user budget of five expensive actions/hour
and fails closed if Redis is unavailable.

Request:

```json
{"bullet":"Worked on reliable API services for customer requests","targetRole":"Backend engineer","skillsToHighlight":["API"]}
```

The shared Zod contract bounds the trimmed bullet to 10–500 characters, role to
100 characters and skills to 20 strings of at most 80 characters.
The success envelope contains `data.rewrites`: three ordered High Impact,
Technical Depth and Leadership/Ownership options. Each contains `action`,
`context`, `result`, assembled `text`, `actionVerb`, `metricPlaceholder`, and
`atsScoreGain`. The gain is the signed shared ATS bullet-preview delta, computed
by the server using requested keywords; it is advisory, not a prediction of a
recruiter's score. Result fields always use explicit placeholders for the user to
replace only with verified evidence.

The service uses LLMGateway with the existing `resume_rewrite` quota. The gateway
currently supports text completions: the JSON output shape is supplied in the
system prompt and the returned JSON is strictly validated locally, rather than
using a provider-native constrained decoding schema. Inputs are escaped and
delimited as untrusted data. Model numbers and taxonomy-recognized skills must
already occur in the original bullet; role/skill preferences do not establish
experience. Schema and evidence failures discard the entire reply.
These checks cannot verify all semantic claims or prevent every hallucination:
users must review responsibility, outcomes and wording before accepting a suggestion.

Validated AI responses are cached for 24 hours by a SHA-256 hash of user, bullet,
role and skills. Raw text is not included in keys, but response values contain
resume text; apply the deployment's normal Redis access/retention controls.
Concurrent identical requests coalesce within one API process. Multiple API
processes can still make duplicate model calls on simultaneous cold misses.
The gateway's own prompt hash is also scoped to a hash of the local user ID.
Cache hits avoid another quota/model call, but still consume the HTTP rate budget.

`mode: "ai"` identifies validated model output. On unavailable/heuristic or
rejected output, `mode: "template"` and `degradedReason` identify uncached
editing guidance: these are prompts to complete, not polished achievement claims.
Template gains are zero. Quota denial remains HTTP 429. Cache I/O failures do not
fail service generation; HTTP traffic still requires the Redis-backed limiter.

No credentials, model API calls, database writes or frontend integration are
needed for the regression tests:

```sh
npm run test:bullet-rewrite --prefix backend
npm test --workspace @devtrack/contracts
npm run build --prefix backend
```

Tests use fixture authentication, provider responses and Redis commands. They
exercise real HTTP routing, shared contract validation and expensive-action
middleware, but do not verify live Clerk, provider output quality, Redis
deployment or production latency. The gateway's existing provider timeouts apply.
