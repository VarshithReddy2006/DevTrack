# Bullet revision ledger

The editable document is a `ResumeVariant`, where the current application stores
`bulletEdits`. In these APIs `resumeId` means that variant's MongoDB `_id`, not
its public `variantId`, the profile ID, or an upload session ID. Every operation
requires the existing Bearer authentication and checks document ownership.

- `GET /api/v2/resume/:resumeId/revisions` returns `{ success: true, data: {
  currentVersion, revisions } }`. Revisions are chronological and include actor
  `userId`, section, monotonically increasing version, timestamp, server ATS score,
  RFC 6902 `patch` and `inversePatch`. The oldest retained record also includes a
  `baseSnapshot` representing the state **before** its patch. Apply successive
  patches to reconstruct each retained version; inverse patches undo them.
- `PUT /api/v2/resume/:resumeId/sections/:sectionId/bullets` explicitly saves a
  section and automatically records its revision. Body: `{ expectedVersion: 0,
  bullets: [{ bulletIndex: 0, originalText: "Original", editedText: "Improved" }] }`.
  An empty array deletes that section. Sections are lowercase, up to 50 characters,
  starting with a letter and containing letters, digits, spaces, `_` or `-`.
  The complete document retains the existing 200-bullet limit. Scores and patch
  operations are generated by the server, never accepted from the client.
- `POST /api/v2/resume/:resumeId/revisions/:version/restore` accepts
  `{ expectedVersion }`. It reconstructs the selected version, restores that
  record's section while preserving later changes to other sections, recomputes
  the current ATS score, and creates a new revision with `restoredFrom`.

These endpoints also have v1 and deprecated unversioned aliases. Reads use the
existing resume read budget; writes use the resume processing budget. Responses
are private/no-store. Unknown documents, foreign documents and unavailable/pruned
versions return 404. Stale expected versions return 409. New and legacy variants
start at version 0. Identical explicit saves do not consume versions; restores
always create a record, including when the content already matches.

The existing flag-gated live-editor variant-generation save automatically records
its initial edits as a whole-document checkpoint (`sectionId: "*"`). Restoring
that checkpoint restores all its bullets. Legacy variants need no migration:
their first explicit section save captures the previous bullets as its baseline.
Version 0 can restore that entire baseline while revision 1 is still retained,
allowing the very first edit to be undone. Once pruned, version 0 returns 404.
The new revision API supports explicit saves; no browser autosave timer is added.

Resume updates, ledger insertion and pruning use one MongoDB transaction with a
version check. MongoDB must support transactions (replica set or sharded cluster);
there is no non-transactional fallback. Concurrent writers using the same expected
version cannot silently overwrite each other. The initial variant-generation
engine still creates a variant before its ledger transaction; if that transaction
fails, the request fails and an unedited generated variant can remain.

At most 50 revision records are retained **per variant**, across all sections.
Pruning advances the oldest baseline in the same transaction before deleting old
patches, so every retained version remains reconstructible. Version numbers are
stored on the variant and never reused after pruning. Historical scores remain
the score at save time; restores are rescored against current profile/keywords.

Validation from `backend/`: `npm run build` and
`npm test -- src/__tests__/modules/resume/bulletRevision.test.ts src/__tests__/modules/resume/variant-v2.test.ts`.
Tests use owned temporary MongoDB replica sets and stub authentication/rate-limit
boundaries; no live Clerk or AI credentials are required.
